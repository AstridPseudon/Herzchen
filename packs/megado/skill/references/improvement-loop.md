# Review-to-action: an implemented improvement loop

## Purpose

**A selected process check exists to improve actual execution, not merely produce a report.** The reviewer identifies supported changes; the accountable orchestrator updates plans and execution, delegates the necessary work, and verifies its effect. A saved report alone is not a completed improvement cycle.

Use this protocol through existing work, documents, decisions, assignments and events. There is no new improvement database, automatic task-graph interpreter, approval panel or required recurring schedule. In the Otto construction portfolio this applies to both the adopted three-hour and twelve-hour checks; other efforts select their own timing and scope.

## Reviewer: return useful direction across the relevant fronts

Look for improvements to the plan and task breakdown, dependencies and priorities, manager/executor context and delegation, useful concurrency and resources, source integration, testing and review economy, tooling and data/authoring UX, implementation architecture, operating instructions and the reusable skill/pack. Examine what the evidence makes relevant, not every category as a ritual. A substantive redesign within scope can be the right correction; “smallest effective change” does not mean cosmetic changes only.

For each supported improvement, state the actual problem and evidence, the proposed change and its scope, an existing accountable owner, the next executable action, expected benefit/trade-off and a useful verification signal. Use the selected normal/XHARD route for executable work where applicable. Distinguish a settled in-mandate direction from a hypothesis needing a discriminating experiment or a genuine request for new authority. Usually prioritise zero to three changes total; do not hide an urgent mandatory defect to fit that convention, or manufacture work to fill it.

## Orchestrator: convert the review into work

By the next coordination turn after receiving the result, reconcile it with current facts and record the necessary decision. **Implement supported, useful improvements within the existing mandate by default.** Do not ask the user to approve each ordinary plan edit, delegated correction or supported protocol improvement again. When the designated scheduled oracle has settled the consequential question, do not commission another oracle to reconfirm the same ruling.

Apply a plan, priority, dependency, brief or resource-allocation adjustment through the canonical path; or give the existing responsible manager a precise instruction to apply it. Delegate substantive code, tests, Git and pack changes to the appropriate owner. Start ready actions promptly; if work cannot start yet, identify its concrete prerequisite and next eligible opportunity. Small managerial updates need not become a new executor task. Larger work can amend an existing task or create a bounded correction. Do not wait for the next three-hour or twelve-hour boundary merely to begin an agreed improvement.

The follow-through is: **review → orchestrator decision → actual plan/assignment change → execution → verification of effect**. A report, a new ticket or an “adopted” label alone is not implementation. Preserve the distinction between action queued, action carried out, and benefit observed; an implemented improvement can still have an uncertain or negative effect.

## Apply an amendment coherently, not only to the summary

Use the ordinary plan-edit/batch path. Identify the current scope and base revision, originating decision, intended task/dependency/ownership changes, relevant instructions, and the affected responsibilities the manager actually knows about. Link the existing decision and operation receipt rather than maintain a second change register. The manager supplies the affected set; software may validate explicit references but does not infer a universal semantic impact graph.

Within one owned authoring scope, apply the permitted changes coherently, preserve concurrent returned results, and emit the existing events/attention for affected responsibilities. Across separate projects, document scopes or owners, finish and release one editing turn before another; link the separate receipts to the same decision and show partial progress honestly. No multi-scope lock or cross-owner atomic transaction is required. If a later scope cannot be changed, keep the affected dependent dispatch on its last valid contract or hold it explicitly; independent work continues.

The next affected assignment uses the adopted current instructions. A running assignment keeps its original pinned brief and history. The manager explicitly chooses to let it finish under that brief, send a bounded amendment with observed delivery, or stop/reassign through the supported host. A queued brief that now conflicts must be refreshed or explicitly disposed of before its next dispatch. Lost notification is not an acknowledgement: the resumed responsibility can retrieve the current revision and unresolved attention. Do not blanket-cancel workers, erase applicable evidence, lower acceptance, reset usage, or change the controlling installation because the plan changed.

This is a convenience and consistency requirement over existing work, documents, operations and attention. It adds no change-control panel, mandatory readback before every edit, automatic re-planner, or migration of every future run.

## Keep the lesson at the right scope

When a finding leads to action, name its intended destination in the existing decision/task context: this effort; a reusable protocol/skill/template; Otto or shared Herzchen tooling; a domain-specific capability; or a pending hypothesis. These labels are protocol guidance, not new kernel enums or routing rules. A correction may legitimately have both a local and a shared destination; give each its existing owner and separate evidence without duplicating the original finding.

Repair the current in-scope problem promptly. Do not wait to build a general solution before making a useful local repair. Do not turn the local workaround into a universal default merely because it succeeded once. For a proposed reusable change, state the applicability and limitations, the actual maintained artifact/operation, and the concrete reason it belongs there. A demonstrated shared defect needs no arbitrary recurrence quota; a local preference or uncertain causal story remains narrower until evidence supports more.

For an adopted reusable change, retain its source diff/adopted revision and the appropriate generated export or installed artifact identity. Add or adapt the smallest regression/example case when it protects a real demonstrated failure or repeated ambiguity; a pure local scheduling choice does not need a permanent new test. During already-planned fixture or fresh-session use, show that a subsequent applicable assignment can discover/use the changed tool or instruction without private coaching. Preserve prior pinned assignments. This checks transfer, not universal effectiveness; no third product build, extra paid agent tournament or new review is required.

A substantial unproved expansion belongs in the existing pending-project mechanism with its evidence and revisit condition. Neither successful integration nor a lesson label activates it. Keep mandatory defects visible as such, and never downgrade one to optional learning in order to finish.

## Exceptions are explicit, not a default backlog

The orchestrator exercises judgment rather than blindly executing every suggestion. Defer for a real dependency, unavailable capacity, explicit sequencing reason or missing authority, with an owner and revisit condition. Reject an unsupported, conflicting, superseded or counterproductive suggestion with the concrete reason. Seek user direction only for an actual unresolved mandate, spending, permission or required-outcome change. A speculative expansion may remain pending; an in-scope execution repair must not be parked merely because it is labelled “optimisation.” Mandatory defects remain blocking where applicable.

Do not change something merely because a timer elapsed. If the evidence supports no useful adjustment, record that conclusion and continue. That is different from receiving an actionable finding and filing it without follow-through.

## Verify and carry the result forward

Use existing task/decision IDs to connect the originating check, actual plan/brief revision or assignment, implementation/test/adoption receipts, and observed effect. Link existing records; do not maintain a shadow improvement ledger. The next relevant check explicitly distinguishes implemented, queued/blocked, untested, effective, ineffective and unobserved work in ordinary narrative/results. It diagnoses avoidable non-execution and reassigns or unblocks it where justified. An evidence-backed reason to defer can remain valid for several intervals; there is no forced deadline or requirement to finish every change before the next check.

Reusable improvements must reach the maintained skill/pack or shared tooling and the applicable active work, not only this run's local notes. Pin the adopted revision, keep the generated file-mode export consistent and tell affected managers what changed. Retain prior instructions for historical assignments; explicitly message/rebrief ongoing work if it needs a changed mandate. Do not generalise a local preference into a universal rule without evidence.

## Separate completion of the change from evidence of benefit

Link the prior observation/baseline, exact implemented version or plan revision, expected signal, actual evidence and uncertainty in the existing result/decision records. Use direct tests or observed use where sufficient. Distinguish not implemented, implemented but effect unobserved, supported benefit, ineffective change, and harmful change in the narrative; these are not a new task lifecycle or compulsory score. An unexecuted experiment is neither a failure nor a successful fix. An implementer can finish the scoped correction while its effect remains an explicitly owned follow-up, without pretending the benefit has been proved or keeping the whole release open for speculative measurement.

A before/after difference does not by itself establish causation; name relevant changes in work, tools, constraints or versions and limit the claim accordingly. Where the change did not help, the manager reverts it if safe and authorised, adjusts it, or retains it for a stated different reason, then observes the result. Preserve the original finding, failed experiment and consumed history. A rollback of content does not undo external effects or refunds. Generalise only the supported lesson, not an assumed success story.

The next useful existing check follows these references rather than commissioning another assurance loop. Closure can be supported benefit, a documented unsuccessful/uncertain result with an appropriate next decision, or justified no-change. A mandatory criterion or unresolved safety defect is never waived by calling the benefit unobserved.

## Boundaries that remain intact

The reviewer is an independent leaf: it does not directly rewrite state, launch workers, certify an unrelated gate, expand budgets or create new privileges. **This separation of roles requires orchestrator action; it does not make improvements optional paperwork.** The scheduler cannot adopt recommendations or make business decisions. The orchestrator uses the normal tools to do those things within the standing authority.

Preserve review independence, consumed allowances, actual clocks and unknown operations. A periodic comparison is not extra product certification. Build/test controller fixes outside the pinned controlling installation and adopt them through the recoverable upgrade path; never edit the live controller underneath its project. Keep source commits and publication on the approved development/fork targets. Use proportionate tests or actual use to establish effects; no second opinion is required merely to close a clearly demonstrated correction.
